# 핸드오프 — 사선 GT 라벨 수정 + sim-to-real 검증 (2026-08-26)

> 시작 과제: sim 사선 카메라 GT의 person 라벨 부풀림 버그 수정.
> 진행 중 라벨 결함 2종을 더 발견해 고쳤고, sim-to-real 예비 실험을 수행했다.
> 아래 모델 수치는 당시 로컬 결과를 옮긴 값이다. 현재 저장소에는 split manifest, 실행 설정,
> 가중치 hash, 원본 평가 결과가 함께 보존되어 있지 않아 독립 재현 전에는 확정 결과로 쓰지 않는다.

## 1. 고친 라벨 버그 (커밋됨)

인스턴스 마스크 → bbox 파이프라인의 결함 3종:

1. **박스 부풀림** (`18cc1ff`) — 색별 min/max에 stray 픽셀이 섞여 박스가 프레임 전체로 커졌다.
   최근접색 판정(절대 상한 없음)이 MSAA 경계·어두운 픽셀을 오분류. → 색별 **연결성분 필터**
   (작고 고립된 stray 제거, 가림에 쪼개진 실제 사람 조각은 보존). 순수 로직 `gtboxes.js` +
   TDD `tests/browser/instance-box-filter.test.mjs`. 실측: 대형 박스 43% → 1%, area 최대 0.67 → 0.075.

2. **팬텀 박스 + 미라벨** (`7b89a3a`) — person 인스턴스가 씬 메시 순서상 equip 수십 개 뒤에
   등록돼 격자색(24,x,y)을 받고, 이웃 equip 격자색과 붙어(색거리 ~32) 최근접색이 카트·설비
   픽셀을 person으로 오분류(팬텀)하거나 person 픽셀을 뺏겨 blob이 줄어 n<80로 드롭(보이는 사람
   미라벨). → person·robot·kettle을 **base 색에 먼저 예약**(색거리 32 → 60~109). 실측: 팬텀 0.

3. **반복 생성 크래시** (`878744d`) — `randomizeScene→randomizeEnvironment`가 설비 원위치를
   첫 호출 때만 잡아, 늦게 로드된 프롭에서 `b0` undefined로 죽었다. → 이름 기준 지연 등록.

부수: 센서 열화 완화 + 천장 배관 벽 밀착(`602c7d2`), imagesOnly 깊이 생략(`15ac4fc`).

### 1.5 화재/연기 씬 부풀림·미검출 — person 라벨을 정확색으로 재구성 (2026-08-26)

위 1·2를 고친 뒤에도 **화재/연기 씬에서 person 박스가 간헐적으로 부풀거나 사람을 놓쳤다.**
사용자가 "라벨링 문제 맞다, 박스가 사람한테 제대로 안 쳐진 게 많다"고 지적 → **이미지를 직접**
확인하니 실재했다(내 자동 지표는 부풀린 박스의 중심이 사람 근처라 놓쳤음 — 눈으로 봐야 했다).

- **근본원인(계측 확정):** person 박스가 `classifyByNearest`(최근접색, **절대 상한 없음**)로 나왔다.
  화재/연기 혼합 픽셀이 어떤 person 색에 "상대적으로" 가장 가까우면 그 색으로 배정 → CC 필터가
  그 먼 성분까지 union → 박스가 프레임을 가로지름. 또 오분류로 person 픽셀을 뺏겨 미검출.
- **해결:** person 은 **정확색(±26) 분류 + CC 필터**.
  · `classifyExact` — 어느 색과도 tol 밖이면 -1. person 색은 서로·배경과 ≥MINSEP 예약돼 있어
    화재·연기·설비 픽셀(색거리 먼)은 애초에 제외 → **부풀림 원천 차단**.
  · 정확색으로 확인된 같은 사람의 조각은 거리가 멀어도 보존한다. 큰 설비에 가려진 실제 조각을
    임의 거리 기준으로 버리지 않는다.
  · 순수 로직 `gtboxes.js` (classifyExact), 회귀 `tests/browser/person-box-region.test.mjs`.
  · (3D 투영영역 게이트도 시도 → 스킨드 메시 world bbox가 randomizeScene 후 stale이라 보이는
    사람을 드롭해 폐기. 정확색만으로 충분.)
- **실측(화재 12프레임 × 정규 박스면적):** person/frame 1.58 → **2.33 (미검출 −47%p 개선)**,
  부풀림(area>0.1) 간헐(최악 가로전체) → **0%**, 박스 최대면적 (간헐 0.67) → **0.042 타이트**.
  눈으로도 12프레임 전부 타이트·사람 위·팬텀 0 확인.
- ⚠️ **교훈:** 라벨 품질은 **자동 지표만 믿지 말고 이미지를 직접 볼 것**(부풀림은 중심-근접
  지표를 통과한다). 사용자가 두 번 옳았고 내가 두 번 과신했다.
- **진행 중:** 이 수정 파이프라인으로 **데이터셋 재생성 → sim-on-sim 검출 @960 학습 → recall
  측정**(트래킹 ID 부여 가능 수준인지). 목적: sim 내부에서 검출→ByteTrack→ID→호모+융합→예측.

## 2. 화면 밖 Chrome 원본 생성 (`acc6e4b` 이후 보강)

브라우저 창을 포그라운드로 유지해야 하던 데이터셋 생성을 **창 없이 백그라운드**로.
`tools/headless_gen/gen.cjs` — Node+Playwright가 화면 밖 headful 창에서 sim을 렌더해 캡처하고
파일을 직접 저장(폴더 선택 불필요). 헤드리스는 WebGL 백버퍼가 0이라 실패 → headful+화면밖+
스로틀해제로 우회. 이 도구는 **분할 전 원본만 생성**하고 `data.yaml`은 만들지 않는다. Git·입력 자산·
실행 환경·장면 seed·전체 장면 조건·카메라별 GT 메타·결과 파일 hash는 `manifest.json`에 기록한다.
생성기가 현재 작업트리 전용 서버와 임시 Chrome 프로필을 직접 만들며, 6카메라 장면은 전부 성공한
경우에만 한 번에 공개한다. 사용법 `tools/headless_gen/README.md`.

## 3. sim-to-real 예비 측정 (재현 자료 보강 필요)

배포 뷰(사선 조리실 CCTV)와 맞는 실사 오픈데이터를 확보: **Roboflow chef1 v5**
(실사 사선 조리실 CCTV, 5,387장, CC BY 4.0). human 클래스만 person으로 매핑 →
`dataset/chef1_person` (train 3767 / valid 1074 / **test 546**).

동일 yolo11n·imgsz640·60ep, **chef1 실사 test**에서 person recall:

| 학습 | → 평가 | recall | prec | mAP50 |
|---|---|---|---|---|
| 실사 chef1 (3767) | chef1 실사 test | **0.970** | 0.967 | 0.977 |
| 우리 sim-A (270) | chef1 실사 test | 0.048 | 0.006 | 0.002 |
| real+sim (4037) | chef1 실사 test | 0.961 | 0.962 | 0.977 |
| 실사 chef1 | 우리 sim (held-out) | 0.057 | — | — |
| real+sim (C) | 우리 sim (held-out) | 0.143 | 0.307 | 0.133 |
| sim-only | 우리 sim | ~0.35 | — | — |

**현재 해석:**
- 이 실행에서는 **실사만 = 0.97**이었지만, 배포 결론은 같은 split과 설정으로 재현한 뒤 확정한다.
- **sim↔real 외형 갭 양방향 ~0.05** — 뷰·라벨·기하를 맞춰도 질감 없는 회색 렌더 sim과 거친 실제
  CCTV는 픽셀이 너무 달라 서로 전이 안 됨.
- **real+sim = 0.961 ≤ 0.970** — sim을 실사에 더해도 검출 이득 없음(미세 희석).
- **C(혼합)의 sim 검출 = 0.14** (혼합비 14:1로 실사 지배) — 단일 모델로 sim+real 둘 다 커버 안 됨.

## 3.5 추가 검증: 4캠 융합 유효 recall + sim GT 트랙 궤적 예측

**멀티캠 융합 유효 recall (sim 검출기 merged_640, 12장면 · person 29):**

| 구성 | 유효 recall | 배수 |
|---|---|---|
| 단일캠 | 0.125 (12/96) | 1× |
| 4캠(코너) 융합 | 0.310 | 2.5× |
| 6캠 융합 | 0.414 | 3.3× |
| 기하 커버리지(≥1캠이 봄) | 29/29 (100%) | — |

한 캠이 놓친 사람을 다른 캠이 잡는 원리 실증(단일 0.125 → 6캠 0.41, **3.3배**). 상한은 sim 검출기가
약해서(0.125)+상관된 미검출 때문. 이 12장면의 기하 커버리지는 100%였다. **실사 4캠 융합 recall은
아직 측정하지 않았다.** 실사 단일캠 결과만으로 4캠 성능을 1.0에 가깝다고 계산할 수 없다.

**sim GT 트랙 → 궤적 예측 검증 (검출기 없이, `eval_traj_split.py`, test set):**

| 예측기 | ADE @1.6s | ADE @4.8s | 안전진입 recall(1.6s) |
|---|---|---|---|
| 칼만 | 0.30m | 1.00m | 0.51 |
| LSTM(minADE@3) | 0.14m | 0.42m | 0.69(전모드) |
| **Transformer(minADE@3)** | **0.12m** | **0.38m** | **0.73**(전모드)·0.89 prec(최빈) |

이 예비 실행에서는 학습형 모델이 물리 baseline보다 낮은 ADE를 보였다. 다만 split·가중치·원본 결과를
보존해 재현하기 전에는 12cm/38cm와 안전진입 recall 0.73을 확정 성능이나 안전성 근거로 쓰지 않는다.

| 축 | 어디서 검증 | 결과 |
|---|---|---|
| 검출 | 실사 chef1 | 0.97 |
| 멀티캠 융합 | sim 12장면 예비 측정 | 단일→6캠 3.3배; 실사 수치는 미측정 |
| 궤적·안전 예측 | sim GT 트랙 | Transformer ADE 0.12m · 안전 recall 0.73 |

## 4. 그래서 방향 (역할 분담)

- **검출 후보 = 실사 데이터 중심.** chef1 0.97 예비 결과는 동일 조건 재현 후 채택 여부를 정한다.
- **sim = ①** 실사로 못 찍는 위험 시나리오(화재·로봇충돌·대피)의 **렌더러 기반 GT** → 궤적예측·안전
  (Trajectron++/risk) **②** 멀티캠 융합·호모그래피·발목 keypoint(기하 기반) **③** 라벨·시나리오 도구.
- **파이프라인(호모+4캠융합+LSTM/Transformer) sim 검증** = **GT 트랙**으로 (검출기 불필요) 또는
  sim-전용 검출기(0.35)+멀티캠 융합(단일 0.35→4캠 ~0.82)으로.
- **ByteTrack**의 실배포 성능은 아직 검증하지 않았다. 재현된 실사 검출 결과와 실제 영상 추적 평가가 필요하다.
- **단일 모델 다리**를 원하면 → **sim 외형 realism 개선**(질감·조명·도메인 랜덤화)이 선결.
