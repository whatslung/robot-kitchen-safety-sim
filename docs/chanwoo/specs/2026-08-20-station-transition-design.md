# 스테이션 전이 모델 — 설계 (확정)

> 2026-08-19 핸드오프 §설계에서 확정된 내용을 스펙 문서로 옮긴 것. 이슈 #2의 1단계.

## 문제

`sim.html`의 `wanderTarget()`은 21개 스테이션을 **균등 랜덤**으로 뽑는다(직전 것만 제외).

| | 값 |
|---|---|
| 균등 랜덤의 평균 이동거리 | 5.51 m |
| 실제 작업 동선(`ROUTE`/`JOB.route`)의 평균 구간 | 0.98 ~ 2.8 m |
| 방 크기 | 11.6 m |

균등 랜덤은 엔트로피가 최대라 **학습할 구조가 없다**. 학습형 예측기가 존재하는
이유는 문맥(직무·현재 위치·사이클 진행도)에 따라 다음 목표의 확률이 **불균등**한
것을 잡아내는 것인데, 지금 생성 모델에는 그 불균등함이 아예 없다. 이 상태로는
학습형이 스테이션 휴리스틱(`PRED.modes`)을 이길 수 없다.

시뮬엔 두 극단만 있고 중간이 없다: `personRoute`(결정적 고정 순서) / `personWander`(균등 랜덤).

## 해결 — 세 번째 모드

기존 `wanderTarget`은 **손대지 않고** 새 모드로 추가한다(기존 데이터셋 재현성 보존).

### ① 직무별 스테이션 집합 + 사이클

| 직무 | 사이클 (스테이션 키) |
|---|---|
| `prep` | `fridge → wrack → island → isle1|isle2 → prep` |
| `cook` | `prep → kettle → panel → nkettle → ntable` |
| `wash` | `sink → store → nrack` |
| `carry` | `serve → isle3 → etable → cartPick → door` |
| `lead` | `panel → robotside → aisle → prep` |

`isle1|isle2` 는 그 단계에서 둘 중 하나를 뽑는다는 뜻(택일 단계).

기존 `JOB.route`와 목적이 다르다: `JOB.route`는 **결정적 순회 순서**(추가 인원용),
`WORKFLOW.cycle`은 **확률 전이의 기준선**이다. 둘을 하나로 합치면 `JOB` 쪽 재현
동선이 확률적으로 변해 기존 데이터셋 생성이 깨지므로 분리해 둔다.

### ② 전이 규칙 (핵심)

현재 스테이션이 직무 사이클 안의 i번째일 때, 다음 목표는

```
p = 0.65  사이클의 다음 단계 (i+1, 순환)                 ← 구조(학습 가능)
p = 0.30  직무 집합 안에서 거리 가중 선택 (τ ≈ 2 m)       ← 현실성(가까운 곳 선호)
p = 0.05  직무 밖 스테이션(통로·입구 등) 이탈             ← 예외
```

거리 가중은 `w(s) = exp(-d(현재, s) / τ)`, τ = 2 m, 현재 스테이션 제외.

현재 위치가 사이클 안에 없으면(모드 시작 직후·이탈 후 복귀) 사이클에서 **가장 가까운
단계**를 현재 단계로 간주한다.

→ 같은 스테이션에서도 직무·사이클 위치에 따라 다음 목표 확률이 달라진다
(불균등·문맥의존). 균등 랜덤과 결정적 `ROUTE`의 중간이고, 정확히 학습형이 잡아낼 구조다.

### ③ 나머지는 기존 것 재사용

체류시간(`STATION.dwell` × 0.6~1.5), 동작(`act`), A* 길찾기, 사람별 독립 시드(`makeRNG`).
사람별 직무는 기존 `SCENARIO`(cook/carry/prep/wash/lead) 배정을 재사용하고,
배정이 없으면 라운드로빈으로 채운다.

## 건드리는 것

`sim.html` 한 파일:
- `WORKFLOW` 테이블(직무 → 사이클·집합) 추가
- `workflowTarget(job, curKey, rng)` 추가 — `wanderTarget()`과 같은 반환 형태
  `{pos, act, dwell, label}` (+ 내부 추적용 `key`)
- `wanderStep()`에 모드 분기 (기존 경로는 그대로)
- 진입점: `__sim.personWorkflow(true)` + 버튼 1개(기존 `🎲 랜덤 움직임` 옆)

### 설계에서 바꾼 것 — 사이클 membership (실측 때문에)

스펙 ①의 사이클을 그대로 넣었더니 **평균 이동이 4.06~5.37 m**로 기준을 못 넘었다.
원인은 사이클을 **설비 이름으로 유추**한 것이다. 좌표로 재보니 이웃 단계가 방 반대편이었다:

| 직무 | 스펙 사이클의 최장 구간 |
|---|---|
| `wash` | `store → nrack` **8.78 m** |
| `cook` | `panel → nkettle` **8.07 m** |
| `prep` | `island → isle1` **7.23 m** |
| `carry` | `door → serve` **7.05 m** |

3칸 고리는 순서를 어떻게 바꿔도 총합이 같아 재배열로는 고칠 수 없다. 그래서 두 가지를 바꿨다:

1. **좌표로 다시 갈랐다.** `JOB` 주석이 이미 남긴 교훈과 같다 — "동선은 자기 구역 안에서
   돈다. 구역을 나눠 놓고 동선이 방을 가로지르면 아무 의미가 없다"(배식구 운반을 서벽에서
   출발시켰더니 도착률 25%). `store`(남동 건조 선반)는 `wash`에서 `carry`로 옮겼고,
   `etable`은 `carry`, `isle2`는 `wash`로 갔다.
2. **사이클에 왕복을 허용했다.** 벽마다 설비가 흩어져 있어 고리를 닫는 순간 방을 가로지르는
   구간이 반드시 하나 생긴다. `JOB.route`가 이미 쓰는 방식이다
   (`wash:["sink","wrack","nrack","isle2","sink","store"]`).

결과 사이클 평균 구간: `prep` 2.74 · `cook` 2.81 · `wash` 1.83 · `carry` 2.49 · `lead` 2.05 m.
남은 최장 구간은 `cook`의 `kettle ↔ ntable` 4.33 m인데, 중앙 조리셀과 북벽 라인 사이에
설 자리가 없어 더 줄일 수 없다.

왕복이 생기면서 같은 키가 두 단계에 나오므로, 사이클 진행도를 **키로 되짚지 않고**
호출부가 숫자로 들고 다니게 했다(`cur.step` → 반환 `step`). 키로 찾으면 늘 앞쪽
단계만 걸려 사이클 뒷 절반이 죽는다.

### 곁가지로 드러난 것 — `jobRole`이 실제 동선을 안 봤다

`jobRole`은 `JOB.route`로 far/caution/danger를 정하는데, WF 모드에서는 `WORKFLOW`
사이클을 걷는다. 세정 담당이 WF에서 로봇에 **6.16 m**까지만 가는데도 route 기준
1.49 m라 `danger`가 붙었다. `WF.on`이면 사이클 집합을 보게 고쳤다.

### 남은 문제 — 역할 라벨이 전부 `danger`로 뭉친다 (이번 범위 밖)

`SAFE.NOM_STOP`이 **3.1 m**, `NOM_SLOW`가 3.9 m다(방을 넓히면서 커진 값). 그런데
5직무의 로봇 최근접이 전부 3.1 m 안이라 `jobRole`이 **다섯 다 `danger`**를 돌려준다.

| 직무 | JOB.route 최근접 | WORKFLOW 최근접 |
|---|---|---|
| cook | 0.73 m | 0.73 m |
| wash | 1.49 m | 6.16 m |
| lead | 1.69 m | 1.69 m |
| prep | 2.42 m | 1.49 m |
| carry | 2.65 m | 2.42 m |

far/caution/danger는 **데이터셋 라벨**이라 다 같은 값이면 하드 네거티브·명백한 음성이
사라진다. WF 도입 전부터 그런 상태였으므로 이번 변경에서 고치지 않았다 — 임계값이
방 크기에 맞는지, 아니면 직무 구역을 로봇에서 더 떼어야 하는지는 별도 판단이 필요하다.
